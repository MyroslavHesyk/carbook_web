# CarBook Web v2 — технічний аудит і результати перевірки

Дата підготовки: 30.10.2026

## 1. Межі аудиту

Перевірено вебверсію, що була в попередньому архіві `carbook_web_version.zip`, та підготовлено нову самостійну структуру CarBook Web v2. Стару базу Telegram-бота не переносимо. Новий Supabase Project має бути порожнім і створюється користувачем.

Перевірка реального підключення до Supabase не могла бути виконана: користувач ще не створив Supabase Project, не виконав SQL-схему й не надав Project URL / Publishable key. Секретні ключі не запитувалися.

## 2. Підтверджені проблеми попередньої вебверсії

| Проблема | Наслідок | Виправлення у v2 |
|---|---|---|
| Кнопка додавання автомобіля використовувала загальний `data-add`, який оброблявся як тип запису | Кнопка могла не відкривати форму автомобіля | Окремі дії `add-car` та `add-record` |
| Запити до всіх таблиць сортувалися за полем `date` | Таблиця `reminders` не має поля `date`, тому запит міг завершитися помилкою | Для кожного типу таблиці визначено власне поле сортування; reminders сортуються за `due_date` |
| Під час редагування запису автомобіль у формі міг братися з активного фільтра | Запис міг бути непомітно переприв'язаний до іншого автомобіля | Форма редагування зберігає початковий `car_id` |
| Статистика використовувала обмеження 200 останніх записів | Підсумки могли не враховувати всю історію | Додано пагінацію запитів порціями по 500 рядків |
| Дата за замовчуванням формувалася через UTC `toISOString()` | У деяких часових поясах дата могла зміщуватися на день | Дати формуються за локальним календарем |
| Не було повноцінного відновлення пароля | Користувач не міг завершити типовий recovery flow | Додано запит листа відновлення та форму встановлення нового пароля |
| Не було окремої сторінки керування експортом і даними | Резервне копіювання було малопомітним | Додано профіль, CSV та JSON експорт |
| Мобільне меню та фільтр автомобіля були непослідовними | Частина навігації/фільтрації була незручною на телефоні | Перероблено мобільну навігацію, drawer та компактний фільтр |
| Візуальна система мала неуніфіковані елементи та слабку ієрархію | Сторінки виглядали як набір різних блоків | Запроваджено єдині компоненти, типографіку, відступи, стани, картки й адаптивні правила |

## 3. Реалізовані частини v2

- Новий адаптивний інтерфейс: авторизація, бічна навігація, мобільне меню, нижня навігація, панель огляду, картки автомобілів, таблиці, нагадування, нотатки, статистика та профіль.
- Supabase Auth: реєстрація, вхід, вихід, відновлення пароля та зміна пароля після recovery redirect.
- CRUD автомобілів, заправок, витрат, сервісних записів, нагадувань і нотаток.
- Перевірка числових полів, цілочисельного пробігу/року, мінімальних і максимальних значень.
- Оновлення поточного пробігу автомобіля після запису з більшим odometer. Помилка цього додаткового оновлення не приховує факт успішного збереження основного запису.
- Пагінація для завантаження всіх записів, а не лише перших 200.
- Фільтр за автомобілем; експорт CSV і JSON включає всі автомобілі користувача незалежно від активного фільтра.
- Розрахунок середньої витрати пального лише за повними інтервалами «повний бак — повний бак».
- SQL-схема з зовнішніми ключами, обмеженнями, індексами, `updated_at` trigger та RLS-політиками.
- Service Worker кешує лише статичні ресурси; API-запити до Supabase не кешуються.

## 4. Безпека

- Frontend використовує лише Publishable key / legacy anon key.
- `sb_secret_...`, `service_role` і пароль PostgreSQL не повинні бути в браузері.
- `cars.user_id` встановлюється за `auth.uid()` на рівні PostgreSQL.
- Child-таблиці дозволяють операції лише якщо пов'язаний автомобіль належить поточному користувачу.
- RLS увімкнено на всіх шести таблицях.
- Користувацькі рядки екрануються перед вставленням у HTML.
- CSV-експорт нейтралізує текстові значення, які могли б інтерпретуватися табличними редакторами як формули.
- Витрата пального розраховується в межах одного автомобіля; пробіг різних авто не змішується.
- Для нового проєкту рекомендується виконати перевірку двома окремими тестовими акаунтами.

## 5. Автоматизовані перевірки

Результати локального запуску Node.js:

- `node --check app.js` — успішно.
- `node --check core.mjs` — успішно.
- `node --check sw.js` — успішно.
- `node --test tests/*.test.mjs` — 14 тестів пройдено, 0 помилок.
- CSS успішно розібрано PostCSS (291 CSS rule node).
- HTML перевірено BeautifulSoup: 58 ID, дублікатів немає, локальні ресурси на місці.
- Перевірено статичні DOM-посилання з `app.js`: усі стартові елементи існують у `index.html`.

Перевірені pure-function сценарії: HTML-екранування, календарні дати, локальна дата, підсумки витрат, витрата пального, порожні/недостатні дані, місячна статистика, статус нагадувань, CSV-екранування та безпечна назва файла.

## 6. Що не підтверджено

Повний браузерний smoke test не завершився: запуск Chromium у цьому середовищі заблоковано системною політикою (`ERR_BLOCKED_BY_ADMINISTRATOR`). Тому фактичний рендеринг у Chromium і end-to-end взаємодію через браузер тут не підтверджено.

До створення Supabase Project і введення власних ключів неможливо підтвердити:

- реальну реєстрацію та доставку email;
- підключення до конкретного Supabase Project;
- фактичне виконання SQL у Supabase;
- створення/редагування/видалення записів у віддаленій БД;
- RLS ізоляцію двох реальних акаунтів;
- password recovery redirect у фактичному GitHub Pages URL;
- резервне копіювання та відновлення на тарифі користувача.

Також поточна версія не реалізує PDF, share links, адміністративні розсилки, автоматичні повідомлення, видалення акаунта та офлайн-запис.

## 7. Рекомендований порядок приймання

1. Створити чистий Supabase Project.
2. Виконати `supabase-schema.sql`.
3. Заповнити `config.js` Project URL і Publishable key.
4. Опублікувати статичні файли на GitHub Pages.
5. Налаштувати Auth Site URL і Redirect URLs.
6. Пройти smoke test усіх CRUD сценаріїв.
7. Перевірити ізоляцію даних двох акаунтів.
8. Налаштувати та перевірити резервне копіювання.

До проходження цих пунктів застосунок є локально перевіреною вебверсією, але не підтвердженим production-рішенням.
